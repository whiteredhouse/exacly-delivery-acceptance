Historical record: [run 41526436188](https://github.com/whiteredhouse/exacly-delivery-acceptance/actions/runs/41526436188)
consumed this trial's full allowance. These instructions cannot authorize a
rerun or replacement installation. See the [supplemental trial](NATIVE-SUPPLEMENTAL-TRIAL.md)
for the separately proposed additional allowance and its required owner approval.

This is a fixed nonproduction trial for existing PR #5 in
`whiteredhouse/exacly-delivery-acceptance`. One continuously alive Ubuntu job
keeps the actual private journal, marker key and installed runtime. It prepares
the exact packet, waits for the owner's post-mint selection, invokes the native
merge once, proves terminal replay offline, then waits for a separate observation
selection. No source test, code merge or environment approval is operation authority.

The original journal cannot be restored from an artifact with the same device
and inode. This trial does not establish recovery after runner or job loss.
Private journal/key/configuration files are never uploaded. Seven-day safe
metadata artifacts retain evidence, rather than a usable recovery installation.

## One job, three steps

Dispatch `app-bootstrap.yml` from the exact reviewed diagnostic source, mode
`native-positive-trial`, with an empty PR input. The fixed run title names PR5.
Only the first attempt is supported. Its ordinary job token has Contents, Actions
and Pull requests read; it cannot post an approval. The existing
`canary-merger-diagnostic` environment must retain its exact diagnostic-branch
restriction, required owner reviewer and disabled administrator bypass. The
owner approves that frozen run in GitHub to release the key for preparation.
The assistant never approves through the same-user connection.

Tools, locked dependencies and tracing are installed before minting. The pinned
official token action requests exactly Contents write, Administration read,
Checks read, Metadata read, Pull requests read and Commit statuses read for only
this repository. Automatic post-job token revocation stays enabled. Mint facts
are explicitly a trusted workflow/action-input attestation and observed
installation output; no retained mint response or provider-expiry claim is made.
The local candidate window is 1,800 seconds, with current time checked by native
code before fresh provider requests. There is no remint or automatic extension.

1. **Prepare:** authenticate the actual run and complete bounded workflow history,
   then initialize one mode-0700 private directory, actual key and journal.
   Configuration, policy, payload, request, identity and operation decision drafts
   are concrete and fingerprinted against the actual installed runtime. No native
   inspector or effect is called. The proposal and exact owner instructions are
   uploaded before the next step waits.
2. **Merge:** restore only the original private installation and authenticated
   relay checkpoint. Wait for the exact owner selection, consume the phase once,
   and call the public native merge CLI. Only the native core evaluates current
   scope, refs, protection, checks, reviews, contracts and credential time. If
   applied, prove exact offline replay and prepare the actual observer packet.
   Upload that separate packet before its wait begins.
3. **Observe:** restore the same installation and remaining relay budget. Require
   a new owner selection that binds the actual retained intent and receipt.
   Run the real bound live-observation test once with its externally selected
   packet digest. A skip, missing receipt or failed observation is not success.

All steps use the same job filesystem and Python installation. Create-only phase
markers prevent replaying an authentic old checkpoint. Restoration verifies
the token binding, immutable documents, source/runtime fingerprints, original
journal UUID/device/inode and original key identity. Relay checkpoints preserve
the total read count, used phases and original clocks; a new step cannot reset
their allowance. Native children receive only their fixed credential selector,
with the separate relay credential and arbitrary GitHub credentials excluded.

## Bounds, uncertainty and retained evidence

The original objective allows one operation, 360,000 ms of native call capacity,
192 native reads and no rollback. Each call is capped at 120 seconds and 64 reads;
only invoke permits its two fixed write calls. This explicitly covers the
supported `UNSTABLE` protocol without silently increasing limits. The separate
one-call observer has its own current, zero-write read decision. The read-only
relay has one total 64-GET allowance across host/history checks and both phases,
at most 25 polls per phase, and no HTTP retries or redirects. The job has a
forty-minute platform limit and bounded step watchdogs.

There is exactly one invocation. A valid uncertain result may use one
same-configuration read-only reconciliation while its original selected
authority remains current and sufficient. No mutation is resent. Rejection,
uncertainty, expiry, partial output or runner loss is never permission to create
a replacement journal, goal, operation or dispatch. Complete history rejects any
earlier native PR5 trial, including failed/cancelled attempts and other sources.
The original author attempts (four plus one supplemental) remain spent.

Offline replay removes the App token from the child and temporarily removes the
actual marker key. A Python network audit and genuine `strace` capture prove zero
network activity; separate socket controls prove both mechanisms work. Exact
receipt, journal bytes/device/inode and restored key inode are checked. This is
historical replay, not a fresh readiness observation.

Only exact safe paths are uploaded: two proposal/instruction pairs and
`merge-approval-receipt.json`, `observer-approval-receipt.json`, `merge-result.json`,
`offline-replay.json`, `observer-result.json`, `trial-report.json`. No raw private
directory, journal, key, token, child stderr/stdout or packet checkpoint is
uploaded. Known applied effects remain applied if a later check fails.
Missing/partial evidence remains incomplete; post-job cleanup must be verified.

A passing result establishes only this one-job positive case, its offline replay
and separately approved observation. It does not establish the remaining live
negative/concurrency/recovery matrix, retention after VM loss, publication,
deployment, runtime health or lifecycle promotion in Exacly's own product model.
